## 1. The game's rule and its evidence

1. **The event removes an aeon from the roster, then fights it.** `sins0700` worker 26: read the roster bit set of the aeons (event native 0x1F2), let the player choose, map the choice to an aeon id (event native 0x1F4), **call removePartyMember (event native 0xCB, handler 0x85B820) with it, then launch that aeon's possession battle**, then read the set again; the Magus Sisters' case also removes Sandy and Mindy; with no bit left the event goes to Yu Yevon (`FFX-G11c` section 7 [R]). `research/re-ffx-last-summoning.md` line 188 says the same from the other side: "the event switched the party flag off with the party-removal native before launching a link, an aeon that was chosen earlier or is being possessed now has no record in that battle and is not in the list". **So the removal comes before its own link's fight: the link's own aeon is already gone in its link.**
2. **What it writes**: the roster flag (bit 0 of the aeon's party-record flag byte, record at 0x1132088 + id * 0x94, via 0x7869B0), its entry in the party order table (0x11307E8) and the three active slots. Not the in-battle availability byte Chr+0xDD4. The battle setup (0x79C110) turns a character's in-battle flag on from the roster flag; the Summon list builder (0x00785410, case 5) lists only the characters whose in-battle flag is on; Grand Summon (0x3118) opens the same list 5. **A removed aeon is absent from the Summon list and from Grand Summon's picker in every later battle, not drawn greyed** [R for both readers, the visible result is [I]: not run].
3. **The script lock** (each possessed copy's init, `setCommandDisabled(1, <its aeon>, 0)`, the byte Chr+0xDD4) alone leaves the row listed and drawn greyed; with the roster flag already cleared the aeon has no record and no row at all, so **the roster removal comes first and the script lock is redundant for the copy's own aeon** (`FFX-G11c` section 7, correction 4).
4. **Our fixed order** (Valefor, Ifrit, Ixion, Shiva, Bahamut; D-651): link 1 (Braska's Final Aeon) all five; link 2 Ifrit, Ixion, Shiva, Bahamut; link 3 Ixion, Shiva, Bahamut; link 4 Shiva, Bahamut; link 5 Bahamut; link 6 none; Yu Yevon none. With no aeon in the battle the Summon and Grand Summon openers answer -3 (type 0x10, empty list) and are drawn greyed (`FFX-G11` section 4).
5. **Grand Summon and a knocked-out aeon**: the entries of list 5 are resolved by the class-0 test 0x0079A080 (HP above 0, availability byte set, left-battle clear, +0x6D8 clear); a knocked-out or recovering aeon answers unavailable (-1), is drawn greyed (the draw loop skips only -4) and a confirm on it is refused (cue 3), the turn kept open (`FFX-G11` sections 4 and 9; the menu-parity lane's `docs/handoff/re-parity-rc11-ffx-menu-parity.md` section 2 and open item 7).

## 6. The submit guard (the main session's ask, ON, no visible change)

The rc11 independent check found that `engine.submit` accepted a hand-submitted command whose row was `enabled: false` (a greyed Escape spent the turn in 1,402 of 1,408 tries, a knocked-out aeon's Summon was taken 414 of 414) and that only the HUD, the strategies, the advisor and the coach refuse them. **Built**: `submit-guard.ts#submittedRowGreyed`, called in `engine.ts#submit` right after `commandRefused` and the Grand Summon rule: the actor's current menu (`availableCommands`, the rows `nextDecision` handed the player) is searched for rows that stand for the submitted command (same kind, id, switch target and escape mode); if there are some and **every one is greyed with no reason**, the command is refused (0 events, the turn kept open). A command with no row at all, and an enemy's, are not this guard's business.

**Why only rows greyed with no reason.** I first built the rule as asked, any greyed row. It left the goldens and the 12-seed identity unchanged but **moved six existing tests**: a row greyed *with* a reason is a refusal the engine already announces with a message and keeps the turn open (Evrae's and Cid's orders "Tidus cannot give that order", the mirror-locked Summon "Mirror of Grothia", the Last Summoning's "Taken by Yu Yevon", and Escape/Flee in a no-escape battle "Can't escape!" with its escape roll, which `research/re-ffx-rng-hit.md` section 6 and `ffx-engine.test.ts` pin). The wider rule would have replaced those messages with silence (`evrae-engine.test.ts` D-08, `isaaru-duel.test.ts` x3, `re-parity-menus.test.ts`, one of this lane's tests), a visible change, so it is **not shipped** (it would be a switch, and it is the main session's call: open item 4). The rows the game draws greyed with **no word** are exactly the ones nothing announces and the executor took: a knocked-out aeon's Summon, a blocked Escape, Flee or Switch, a Cursed actor's Overdrive (all `MENU_DRAW_PARITY` rows), a formation's switched-off command (already refused by `commandRefused`). So with every switch off **no menu holds a reasonless greyed row the engine did not already refuse, and the guard acts on nothing**; it acts only on the rows the parity switch adds.

**Survey** (a scratch script: every greyed row of every party member of 14 chapters plus every aeon down, submitted by hand on a fresh engine, the tip without the guard, then with): parity off, 83 greyed rows tried: 14 Flee rows ("Can't escape") and 13 trigger rows (Talk, the Evrae orders) are accepted, all with reasons and so not this guard's, the other 56 are refused already, with or without a message, **identical with the guard**; parity on, before the guard 53 Escape rows and 51 Summon rows were accepted (action-start), **with the guard all 54 Escape and 51 Summon rows are refused silently**; the 10 Evrae order rows keep their message. **Proof that nothing moved**: 192 of 192 plays identical to `4028a3466` with the guard in, switches off, and 192 of 192 identical with `MENU_DRAW_PARITY` on (event logs, menus, outcomes, turns); the four goldens and the pins pass (section 8).
