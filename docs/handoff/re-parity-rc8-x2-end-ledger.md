## 2. How it is built

- **Kernels** (`src/battle/ffx2/kernel/`, pure, no DOM, no `three`, no draw):
  - `item-ledger.ts` (347 lines): the stock count (0x620ba0), stock add or subtract (0x620e80: the 68-slot table, the 99 cap, the gained and used bitmaps), the gil routine (0x60d4b0), reserve (0x620d90), refund or commit (0x620c00), the start gate (0x6314c0: the five checks in the game's order, a pass is the commit), queue add (0x62d300, at the tail, the handle `(sequence << 8) + chr`), cancel one (0x62d120) and the cancel family (all, by handle, by command id, the knock-out's cancel) as one walk over a queue of up to eight records. The per-kind level counters and the queue's ATB state byte (the animation machine's bookkeeping) are **not** ported.
  - `battle-end.ts` (269 lines): the evaluation (0x61ef70) and the tail of the logic step (0x61e440: the calls in order, the pause press, the abort path that never runs, the teardown and the report at phase 0x26 or outcome 5, outcome 6's report without teardown).
  - `battle-end-commit.ts` (395 lines): the whole post-battle machine (0x61e7a0), phases 1, 2, 0x1A, 0x1B and the presentation phases 0x1C to 0x25, so the machine is proved as a whole; each callee is a `host(address, ...args)` function the caller answers.
- **Adapters** (`adapt/`): `item-ledger.ts` lays one item's stack out as the kernel's one-slot table (the kernel's functions look at no other slot but to find a free one, and the stack's own emptied slot is always free, so a one-stack table answers as the whole table would) and runs the kernel on it; `battle-end.ts` turns the engine's units into the kernel's characters (reused buffers: the evaluation runs after every step and every action) and the codes into outcomes, and counts queued and running work for the drain test.
- **Engine**: `Ffx2Unit.itemHold` (`internal.ts`, engine-internal like `autoWords`: not a contract file, no `docs/CONTRACT-CHANGES.md` entry); `execute.ts` reserves before `beginCharge`, commits where the item was spent, aborts with a message when the stock has none; `engine.ts#submit` and `engine-core.ts#fireHeld` refuse an item pick the reserved stock cannot make (the turn is not spent); `end-window.ts` (new, 130 lines) is `EndWindow`, which drives the kernel's machine with a host that answers for the engine; `engine-core.ts#checkBattleEnd` asks it, `nextActor` returns nobody but a held command while it is open, `inputValid` is false while it is open, `fork` copies it, and `FFX2Engine#endWindowStats()` (deliberately not on the `FFX2BattleEngine` interface) exposes its counters. `results.ts#battleOutcome` is the kernel's evaluation. `adapt/streams.ts` states that none of this draws.
- **400-line rule**: `engine-core.ts` is 396 lines (it was 396; its import lists were compacted to make room), `engine.ts` 368, `execute.ts` 328, `internal.ts` 392, `results.ts` 104; `battle-end-commit.ts` is 395.

## 3. Decisions made on the way (each is a boundary or a stand-in, not a game number)

1. **Result 3 is not turned into an escape (XK3 is gated).** The kernel returns 1 (party gone), 2 or 4 (won), 3 (nobody left in the battle, a girl alive: ejected or escaped). The adapter maps 1 and 3 to `defeat` and 2 and 4 to `victory`; result 3 therefore ends a fight exactly as the engine ended it before (`partyAlive` already dropped a removed girl; `leblanc-engine` A7, "all three ejected is a defeat", still holds). The window's `lastCode` records the game's 3. What the events do with result 3 is unread (G10 open questions 11 and 12).
2. **Parts are fed as "not present".** The kernel implements "parts gate unless out of battle or not present"; the engine's standing rule is that parts never gate victory (the Leg's Nodes carry 300,000 HP), and how the game's scripts take the Nodes and the Experiment's parts out of the evaluation was not traced (G10 open question 9; rule 6). A part's cast still holds the window (it is queued work), which is how a part's Phoenix Down on a fallen boss cancels the end.
3. **What counts as "queued" in this engine.** A cast on the purple bar whose owner is not asleep, petrified or Stopped (the game's own exclusion: G06 3.5, G10 10.2); a command held back for a chain lock; a suspended timed input; a command in its action time (the E4 estimate, off by default). An idle wait is not a command. The engine resolves a command with no charge in the call that picks it, so only charges can be in flight.
4. **Inside the window** no menu is offered, no monster script is polled and nothing new starts; only a held command may fire when its lock lifts. The machine's "close every menu" is the engine's `closeMenu` (a girl in the waiting-for-a-command state goes idle, the input owner is dropped).
5. **A safety cap**, `END_DRAIN_CAP_STEPS` = 3,600 logic steps (two minutes), closes a window that cannot drain by dropping what is left. It is an engine guard against a hang, not a game number. It was reached in none of the 5,000+ windows measured (the longest wait was 453 steps, 15 seconds, in Chapter XIII).
6. **Refund timing differs from the note's reading in one place.** `settleGauges` (existing, X2-A's) drops a Stopped or Petrified girl's charge at once, where the note reads the game as leaving the record queued until a KO or the battle's end (G06 3.7, [R] not [E]). The ledger refunds at the drop. The stock a player sees at the end of the fight is the same. Not changed here.
7. **A command held for a chain lock reserves its item when it fires**, not when it was confirmed (the engine keeps a held command outside the queue). Rare; the menu then shows the old count for the lock's two or three seconds.
8. **An item the battle does not track** (no `inventory:<id>` flag: a test rig, a script) is free, as before; a monster never reserves (so a monster's item command no longer touches the party's stock, which the old code did).
9. **Gil is left alone.** `reserve` handles gil as the game does and the kernel proves it, but no UI sets an amount (no picker exists), so XF2 stays a plan: `resolve-strike.ts` still spends a Bribe at the strike and Spare Change is still free.
