## 2. How it is built

- **Kernel** (`src/battle/ffx2/kernel/grid-path.ts`, 193 lines, pure, no DOM, no `three`, deterministic, no random draw): `gateNumber`, `dressNodes`, `allDressNodesVisited`, `gateState`, `findPath` (the finder: a direct join first, else a gate neighbour of A that B also touches, in the card's slot order = ascending link id, which only a node's path to itself can see), `movePairs` (the finder over every unordered pair of dressphere nodes), `moveRecord` and `commitMove` (the three modes), and `ringOrder`. The existing `kernel/spherechange.ts#gateSlotsAfter` (proven on its own) turns the crossed gates into the girl's eight gate-ability slots; the walk vectors compose the two.
- **Our numbering of a grid's nodes (`ringOrder`)**: the game has no "node 0" and lets the player put a dressphere on any node; the builds place their dresspheres for a ring (`setup.ts#gridNodeContents`: node `i` beside node `i+1`, node 0 beside the last), and the real grid's cards number gate nodes among the dressphere nodes. The engine's node `i` is the i-th dressphere node **along the lowest ring through the grid's real joins** that starts at the card's first dressphere node (62 of the 64 cards have one, every covered grid among them; plates 33 and 63, which our data does not name, keep the card's order). Consequence, proved by tests: **every Change a build could make before it can still make** (node 1 first, the last node last, the same dress) and the real grid adds the joins it has beyond the ring. Without it the builds' designed Changes would break arbitrarily (Paine could not reach her White Mage in Chapters V, XI and XV, Yuna not her Gunner). It is our convention, a label of an estimate, not a game fact; it is one function.
- **Adapter** (`adapt/grid-layout.ts`, 48 lines): `linksFromLayout` turns the finder's pairs into the engine's links (`from` below `to` in engine nodes, ascending by `(from, to)`, so a node's Change rows come out in ascending destination order, as a ring's did apart from its wrap), each with the gate colour of the layout's table; `layoutNodeCount`. `adapters.ts#garmentGridRegistryFrom` reads `layout` from the data grid and falls back to the old ring when there is none.
- **Data** (`data/ffx2/garment-grids/`): `layouts.ts` (263 lines; the file the addendum said cannot go into `early.ts` or `late.ts` under the 400-line rule), `types.ts#GarmentGridLayout`, `index.ts` attaches each layout to its grid. `internal.ts` (389 lines) and the engine's `GarmentGridDef` are **unchanged**: the links already carry everything a move needs, so no field was added to the engine's grid.
- **Switch**: `constants.ts#GRID_LAYOUTS = true`; false restores the ring estimate for every grid (checked: with it off the six moved Road logs return to their old digests, and the 12-seed measurement of every chapter equals `origin/r49-rc`).
- **The fallback table** (`garment-grids.ts#GRIDS`, 19 rings, read only when nothing is injected) is **unchanged** and still an estimate; the tests that inject nothing keep their rings. The live screen injects the data's registry (`BattleScreenContent.ts`).
- **No shared contract changed**: `battle/common/types.ts` and the other contract files are untouched, so there is no `docs/CONTRACT-CHANGES.md` entry. `GarmentGridState` (`passedGates`: colours) is as it was.
- **RNG**: the grid rules draw nothing (G09 summary 11), so the stream registry needs no row.
- **400-line rule**: `adapters.ts` 204, `constants.ts` 259, `kernel/grid-path.ts` 193, `layouts.ts` 263. `node tools/orphans.mjs`: the new modules are reached from `src/main.ts` (the only orphans under `src/battle/ffx2/kernel/` are `dressphere-recalc.ts` and `spherechange.ts`, as before).

## 3. Sources and the proof against the game

The note's proofs ran the live exe's own machine code in the harness against an independent model written from the disassembly, over all 64 real cards: the gate number `0x005eb2a0` (690 vectors), the every-node-worn test and the gate state `0x005eb920` / `0x005eb7d0` (10,724), the path finder `0x005eb080` (4,056: every ordered pair of nodes of every grid), the commit `0x005f51a0` with the gate evaluation `0x005f4170` on the real plate rows (4,173 walk vectors: 989 / 1,390 / 1,966 paths of kind none / direct / through a gate; modes 3,356 / 412 / 405) and 6,000 synthetic-row vectors for every condition code: **0 mismatches in every group**. I did not re-run the harness; the vectors are the note's, and the kernel replays them.

- **The fixture** `tests/fixtures/parity/ffx2/grid_path.json` (4,474 vectors, 732 KB; the game's own answers) is a stratified subset: `gate_number` 690 (all), `gate_state` 1,280 (20 a plate, with masks that have bits above the grid's last node), `path` 1,480 (every ordered pair of dressphere nodes, 1,100, and up to 6 other pairs a plate: a node to itself, a gate at either end), `walk` 1,024 (12 ordinary moves and 4 Special entries or exits a plate). It also holds **the 64 cards as numbers** (`layouts`: nodes `[gate, x, y]`, links `[a, b]` by link id), converted from the note's `grids.json` (checked in the conversion: each link joins exactly two nodes and link ids are 0 to L-1; checked when the data was read, in a scratch script: the neighbour slots of every node are in ascending link id on all 64 cards, which is why the kernel derives them from the link table, and the self-pair vectors, the one place the order shows, replay with it). The walk file lists steps without their starting state (runs are consecutive lines), so the generator rebuilt each run by continuity: 4,173 steps in 1,101 fresh runs, and every one of the 4,173 replays with the kernel (so the stored `before` states are consistent with the game's outputs); the stored outputs are the game's.
- **Static facts of the cards, asserted by the tests**: at most 10 nodes and 13 links (the visited and crossed masks are plain numbers); 206 gate nodes, each with exactly two neighbours, both dressphere nodes, no gate touching a gate, each gate number at most once on a grid; 192 unordered dressphere pairs joined directly and 206 through one gate (the note's 3.2 table), never both for a pair and never two routes for a pair (so the order of a node's neighbour slots decides nothing but the path of a node to itself); the shipped layouts equal the cards of their plates, node for node and link for link.
- **Beyond the note, checked here against the game's own rows**: the plate row's always-on bytes equal each covered grid's equip stats; the node field of the plate row equals the data's node count for the 39; the data's colour-keyed pay-off equals the plate row's for every set of gates crossed (section 1, XI3); the 39 single-colour effects sit on the ability the plate row puts at their colour's number (ability ids matched to our descriptions by the game's own names when the tables were written; only the ids are kept).
- **Ours, not the game's**: `ringOrder` (the numbering), the Change rows' ascending order, the `colourOfGate` tables, `GRID_LAYOUTS`.
