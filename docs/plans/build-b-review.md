# Paper critique: Build B (the twelve approved presentation changes, game-aware)

Critic design review, 2026-09-19. Verdict: **revise**. Required changes first.

## 1. REQUIRED 1 — The twelve have no approved tile in docs/target/targets.json, so Build B caps Part C at 8.0 on the day it ships

**Why:** Verified: the `polish` group in docs/target/targets.json (lines 109-116) is a single tile, state `gap`, note "Nothing is built until you pick." RUBRIC.md:67 caps Part C at 8.0 for "a new player-facing feature, screen or restyle started after 2026-09-18 with no approved target" — and today is 2026-09-19. round-02.json recorded that cap as "not established ... non-binding at 5.30" only because nothing yet qualified; twelve items qualify at once. Note the cap says *restyle*, so items 2, 4, 11 and 12 qualify even though their code partly exists. Bailey's approval lives in chat and in docs/concepts/polish/board.json; the Part C scorer reads neither.

**Change:** Before the first line of code, commit each of the twelve into docs/target/targets.json as its own tile with `state: "approved"`, `evidence` quoting Bailey's own words from this request verbatim, `src` pointing at docs/concepts/polish/<id>/after.png, and a `build` field naming one capturable moment (e.g. "Chapter select, chapter 1 highlighted, silhouette cards settled"). Retire the single `gap` polish tile in the same commit. Put them in a new `motion` group with its own weight, or re-weight `whole, polish` up from 5 — five points cannot carry twelve features.

## 2. REQUIRED 2 — The named source of truth for the FFX / FFX-2 split does not exist

**Why:** research/ contains only assets-and-tech.md, ffx-bfa-yu-yevon.md, ffx-combat-core.md, ffx-seymour-flux.md, ffx-yunalesca.md, ffx2-bahamut.md, ffx2-combat-core.md, ffx2-vegnagun-shuyin.md, visual-bible.md, writing-bible.md and data/. There is no ffx-vs-ffx2-presentation.md. Items 8, 9, 11 and 12 define their cross-game halves purely by pointing at it ("whatever research says its battle intro really is", "FFX-2 gets its own researched transition"). Bailey's rule — apply a change only to the game it is true to — is unverifiable against a file that is not written, and the owner's rule is the one thing this build must not get wrong.

**Change:** Gate Build B's start on that file landing, one row per item: item id, game, the canonical behaviour, the citation into research/ffx-combat-core.md or research/ffx2-combat-core.md, and an explicit "no canonical equivalent — do nothing here" where that is the honest answer. No item ships its cross-game half before its row exists. Items whose row says "no equivalent" ship as a documented no-op for that game, not as an invention.

## 3. REQUIRED 3 — ctb-preview's headline example is the one case the engine cannot preview: Delay, Haste and Slow all preview as no change

**Why:** src/battle/ffx/turnQueue.ts:281-316. `predictTurnOrder(ctx, n, previewCommand)` resolves previewRank from the ability (line 290-292) and then applies it only to the *acting* character's own recovery, and only on the first iteration (`const rank = first && previewRank !== null ? previewRank : 3`, line 311). It never calls `applyDelay` (line 125) or `onHasteApplied` (line 141), which are the functions that move a *target's* counter. So Quick Hit (rank 1 on self) previews correctly, while Delay Buster, Delay Attack, Haste, Slow and Threaten preview as identical to a plain Attack. The plan's claim that this uses "the engine's own CTB simulation (tick, rank, Haste, Slow, Delay, Quick Hit)" is false about the current code, and the card's own pitch — "choosing Quick Hit over Delay Buster becomes a read rather than a guess" — is exactly the comparison it would get wrong. A confidently wrong CTB preview in a game about CTB is worse than no preview.

**Change:** Extend the solver before the UI: add an optional preview path that clones the runtime counters and applies the command's target-side effects (applyDelay for delay-strength abilities, the Haste/Slow half/double on the target's current counter and future recovery, rank-3 re-entry for a revive, removal of the party and insertion of the aeon for Summon). Pin it with unit tests in tests/unit against known agility/rank pairs and against a Delay Buster on a Threatened and on an immune-to-delay enemy — both of which applyDelay already refuses at line 128. Until those tests pass, ctb-preview does not render.

## 4. REQUIRED 4 — "Build B starts after Build A lands" is load-bearing and Build A is 26 blockers on a tree that does not compile

**Why:** critic/rounds/round-02.json: headline 3.5, Part A 5.62, Part B 3.48, Part C 5.30, 45 ranked issues of which 26 are blockers — including Chapter 4 never ending, Yu Yevon being an infinite battle with no exit, seven Chapter 5 combatants rendering the placeholder silhouette, and "Paine — and every boss, aeon and dressphere — ships live as a letter in a box". Issue #44 records that the working tree does not compile from uncommitted edits, and `git status --porcelain` currently returns 566 entries. A parallax title screen in front of a game where Chapter 4 cannot be exited moves the headline nowhere: Part B's Game feel, Clarity and Onboarding are 12/12/10 weight and all three are held down by blockers, not by polish.

**Change:** Make the gate on Build B's start explicit and checkable, not aspirational: the tree compiles, `npm run build && npx playwright test` passes, Build A is committed to main and deployed, and a critic round has run on that live build. State in the plan which of the 26 blockers Build A closes and which it does not — Build B is not allowed to be the reason a blocker slips.

## 5. REQUIRED 5 — Items 11 and 12 are not new: ChainCounter.ts and SpherechangeFlourish.ts already exist as untracked files from the in-flight FFX-2 HUD track

**Why:** `git status --porcelain` shows `?? src/ui/ffx2/ChainCounter.ts`, `?? src/ui/ffx2/SpherechangeFlourish.ts`, `?? src/ui/ffx2/spherechange-flourish.css` and `?? src/app/screens/BattleEncounterChain.ts` — untracked, uncommitted, unreviewed — alongside modified `src/ui/ffx2/FFX2BattleHud.ts`, `CommandMenu.ts`, `PartyRows.ts` and `ffx2-hud.css`. src/ui/ffx2/SpherechangeWheel.ts is already tracked and shipping. ## 6. REQUIRED 6 — "all reduced-motion safe" and "a working lowEffects path" have nothing to attach to: BOTH settings are dead fields

**Why:** `lowEffects` appears only at src/app/SaveData.ts:60 and :147 and in a comment at src/app/screens/PauseScreenPanels.ts:202 — round-02 #19, measured beside 0.4 fps sustained in the battle scene. `reduceMotion` is the same: src/app/SaveData.ts:61 and :153, and the same comment at PauseScreenPanels.ts:203, which says out loud that these "belong to a settings screen" — one that does not exist. The only reduced-motion honouring in the codebase is CSS `@media` in the HTML layer plus a direct `matchMedia` call in src/ui/inkgold/wipe.ts:71. Neither reaches Three.js, so items 4, 6, 7, 8 and 10 — every WebGL item — have no reduced-motion path at all regardless of what the plan promises, and a player cannot turn any of it off.

**Change:** Build one EffectsBudget module first and make it a hard prerequisite: tier derived from lowEffects + reduceMotion + prefers-reduced-motion + a rolling frame-time watchdog that auto-offers the low tier above ~33 ms for two seconds; expose the resolved tier on window.__pyrefly; add a GRAPHICS and a MOTION row to the pause menu so the settings become reachable; require each of the twelve to register its cost and its degraded form with it. Acceptance is one capture per tier, not per item.

## 7. REQUIRED 7 — The build adds seconds to a game the critic just measured at 2-4x its source length with no skip

**Why:** round-02 #16: chapters run 2-4x the fights they recreate with no checkpoint and no speed control a player can find; #30: Confirm cannot fast-forward a cutscene and there is no skip prompt. Build B then adds per-screen ink wipes (item 2), a sweep before every retry (item 8), the shatter (item 9), a dissolve with a beat of quiet (item 10) and a spherechange sequence per change (item 12) — a Chapter 2 retry pays all of it again, and a first-timer retries most. `skipSeenCutscenes` is a third dead field (SaveData.ts:58, :146; only mentioned in a comment at src/app/screens/CutsceneScreen.ts:89), so the obvious mitigation is not wired either.

**Change:** Make a global Presentation Speed (Full / Short / Off) plus a live "already seen" set a prerequisite of Build B, not a per-item option: wire skipSeenCutscenes, have all twelve read one presenter timeScale and that one seen-set, make Confirm interrupt a running sequence rather than queue behind it, and make every added sequence collapse to zero under the existing `speed: 'skip'` debug path so the e2e sweep does not get slower.

## 8. REQUIRED 8 — living-backdrops rewrites a module that already does most of it, and cannot fix the scene defect it appears to address

**Why:** docs/ARCHITECTURE.md:107 describes src/engine/Backdrop.ts as already building "a parallax stack: the painting on a far plane, masked parallax layers cut from bands of the same painting, a lit 3D ground plane tinted from the painting's own bottom rows, drifting mist, matched fog and background". Item 4 is therefore a rewrite of a shipped system, not a new one, and the plan does not say so. Worse, the scene problem the critic actually found is round-02 #39 — Zanarkand Dome reads as an open-air flooded twilight ruin rather than Yunalesca's sealed dark hall — which is a content defect item 4 is explicitly forbidden to touch. Adding depth to a room that reads as the wrong room makes the wrong room move.

**Change:** State plainly that item 4 extends Backdrop.ts (name the file), and list what is genuinely new: inpainted hidden regions behind the cut bands, a floor/sky split, and shader ambient motion. Separately, say in the plan that #39 is out of item 4's scope and name who owns it. Keep the approved PNG shipped and loaded unchanged as the flat fallback (lowEffects, reduced motion, decode failure) and as the hash reference; write plates to public/art/backdrops/<scene>/plate-N.png; add a check that recomposites the plates at pan 0 and asserts a perceptual delta below a stated threshold against the approved file. The `scenes` group is the only Part C category scoring above 9 (9.5), its Zanarkand tile records sha256 f48c5b05… and the 5.0 "approved painting replaced" cap is live.

## 13. REQUIRED 13 — pyrefly-death has no per-enemy classification, and the three new chapters break the taxonomy it does have

## 14. REQUIRED 14 — Ten of the twelve are motion with no sound named, on top of a live audio blocker

## 16. OPTIONAL 16 — ctb-preview is an assist FFX never had, and its refusal list is unenumerated

**Why:** FFX shows the order; it never previews the consequence of the command under the cursor. A veteran will read an always-on predictor as easy mode bolted onto the one system these fights are about, and a record set with it on is not the same record. The card's rule ("refuse to guess where a move's cost is random or conditional") is right but unlisted, and the hard cases are real: Summon removes the party and inserts the aeon, Talk has no rank and currently does nothing (#12), Mix and the reel Overdrives have no deterministic cost. Firing on every cursor move also thrashes the list as the player arrows through eight abilities.

**Change:** Write the refusal list into the plan — summon, dismiss, switch, Mix, reel and timing Overdrives, Talk, any random rank — and render those dimmed with "outcome varies" rather than ghosted slots. Add a PREVIEW option (Always / On demand / Off), default On demand on a held key, so a veteran can decline it. Debounce on ~120 ms of cursor dwell.

If five, write into the plan that items 1, 4, 6, 7 and 10 each take a second pass when the chapters land, so their boards are not approved twice.

## 18. OPTIONAL 18 — Evrae asks item 5 a question the CTB preview is not built to answer

**Why:** That fight's mechanic is distance: Cid moves the ship, and at range only Wakka, Lulu and the missiles reach, while closing restores melee and brings on Poison Breath, telegraphed by the inhale. A command that changes reachability is not a turn-order change, so a CTB preview answers the wrong question in the one chapter built around asking it — and the panel that would carry the inhale telegraph is round-02 #14's blocker, the intent slab that covers the boss, the second enemy and both reticles.

**Change:** If Evrae lands, widen item 5's contract from "the resulting turn order" to "what this command changes", including the distance state and which party members go dark at the new range, and make the telegraph part of the same read. If Evrae does not land in this build, scope item 5 to the three existing FFX chapters and say so in the plan.
