## 2. What the game does (the rules, with the evidence)

1. **The event removes an aeon from the roster, then fights it.** The field event `sins0700`, worker 26: read the roster bit set of the aeons (call 0x1F2), let the player choose, map the choice to an aeon id (0x1F4), **call removePartyMember (call 0xCB, handler 0x85B820) with that id, then launch that aeon's possession battle**, then read the bit set again; the Magus Sisters' case also removes Sandy and Mindy; with no bit left the event goes to Yu Yevon (`FFX-G11c` section 7 [R]; `research/re-ffx-last-summoning.md` sections 0, 2 and 5: "the chosen aeon is taken out of the party before its battle", line 188 "the event switched the party flag off with the party-removal native before launching a link").
2. **What the removal writes**: the roster flag (bit 0 of the aeon's party-record flag byte, record at 0x1132088 + id * 0x94, via 0x7869B0), its entry in the party order table (0x11307E8, written 0xFF) and the three active slots. Not the in-battle availability byte Chr+0xDD4 (that is the script lock's byte). The battle setup 0x79C110 sets a character's in-battle flag Chr+0x10 from the roster flag, and the Summon list builder (0x785410, case 5) lists only characters whose Chr+0x10 is set. **So a removed aeon is not on the Summon list or in Grand Summon's picker (the same list 5) in any later battle, and it is absent, not drawn greyed** (`FFX-G11c` section 7 [R] for both readers; the visible result is [I], not run). Timing: the removal comes **before** its own link's fight, so the link's own aeon is already gone in its link.
3. **What the script lock adds**: each possessed copy's init makes `setCommandDisabled(1, <its aeon>, 0)` (the availability byte Chr+0xDD4). The list builder never reads that byte, the draw loop greys what the class-0 test (0x79A080) refuses, so the lock **alone** leaves the row drawn greyed. With the roster flag already cleared the aeon has no Chr+0x10 and no row at all: **the roster removal comes first and the script lock is redundant for the copy's own aeon** (`FFX-G11c` section 7, correction 4).
4. **Per link in our fixed order (Valefor, Ifrit, Ixion, Shiva, Bahamut)** (`FFX-G11c` section 7 table): link 1 (Braska's Final Aeon) all five; link 2 Ifrit, Ixion, Shiva, Bahamut; link 3 Ixion, Shiva, Bahamut; link 4 Shiva, Bahamut; link 5 Bahamut; link 6 none; Yu Yevon none. With no aeon in the battle Summon and Grand Summon are the type-0x10 openers the resolver answers -3 for, so they are **drawn greyed** (`FFX-G11` section 4 and the empty-opener list).
5. **Grand Summon and a knocked-out aeon.** Grand Summon (0x3118) opens the same list 5; its entries are resolved by the same class-0 test (HP above 0, +0xDD4 set, +0xDCD clear, +0x6D8 clear). A knocked-out or recovering aeon answers unavailable, the resolver -1, the entry is drawn greyed and a confirm on it is refused (cue 3): `MENU_DRAW_PARITY`'s handoff section 2 and open item 7.
6. **Talk after use.** `FFX-G11b` section 5: Talk (0x3105) is added by four formation scripts and removed by `removeCommand` after the character's line (Chapters I and X once per character, Chapter VII per speaker by Seymour's script and the formation scene, Chapter III after the third use). The engine keeps a greyed row. Research only here (item 4); Braska's Talk row greyed while pending was approved by Bailey on 2026-10-09 (D-659) and is not changed.

## 6. Risks

- **A removed aeon is also the possessed copy's source.** The copy's stats are read from the player's own aeon at the battle's start (`ai/possession-setup.ts`), so the roster entry must stay in `aeonRoster`; removal is a flag read by the lists, never a deletion.
- **Strategies and the advisor read rows and `availableAeons`**; a removed aeon has no row and is not in `availableAeons`, so nothing can choose it. A Grand Summon with no aeon left is greyed and refused (a strategy filters on `enabled`).
- **`structuredClone` forks** (the advisor's look-ahead) copy `state.flags`, so the removal travels with a fork (tested, like the lock's).
- **Hidden Chapter 28**: the field is stripped from its copies of Yu Yevon's group, and the parity change only hides a row; both are pinned by a test and by the switch-off identity.
